# Phase 3 verification

Status: first written on 31 October 2026, at commit `f787f2a`, after implementation steps 1 to 11 and `finish --rebase` were marked complete in the [PRD](PRD.md). Updated on 5 November 2026, at commit `c26b04b`, after the Pi extension and skill from step 12 and the first real run in Pi. Step 12 is in progress: Claude Code as a second host is not started. Criteria 2 to 9 and 11 to 13 are met. Criterion 1 is met except for the step runner and the dispatcher loop, which are used by `finish` only, and criterion 10 is met except for two parts the real run did not show (see [Not yet met](#not-yet-met)).

The root suite (`npm test`) passes under Node.js 26.7.0 on macOS: 996 tests, 994 passed and 2 skipped (platform-specific), at `c26b04b` on 5 November 2026.

This record maps each acceptance criterion in the PRD to its evidence. Unless stated otherwise the evidence is a test in `tests/`. Unlike the Phase 2 record, this record was written after the steps were implemented, and not every safety check was disabled in turn to confirm that a test fails without it. Where that was done, it says so.

## Acceptance criteria

1. **One database.**
   - Every connection sets `synchronous = FULL`, with `fullfsync` (`src/database.ts`). Database durability, the schema version and canonical paths are covered by `tests/tasks/sqlite.test.ts`.
   - Tasks, dependencies, readiness, holds and definition revisions are in SQLite (`tests/tasks/sqlite.test.ts`, `tests/tasks/commands.test.ts`). Switchboard reads and writes tasks without tasks-axi; tasks-axi remains a dependency only so that `import --tasks-axi` can use its parser.
   - The import (`tests/tasks/import.test.ts`, `tests/attempts/import.test.ts`, `tests/attempts/runtime-import.test.ts`) uses tasks-axi's parser, refuses unfinished attempts, possibly running workers and fresh dispatcher heartbeats, validates a staging file before activating it, leaves the original data unchanged after a failure, can be run again, and imports file-based records including pruned attempt numbers and reservations without an attempt.
   - A process killed inside a reservation transaction leaves no records and no lock (`tests/attempts/store.test.ts`, `tests/dispatch/transaction.test.ts`). A busy database refuses while heartbeats and stop handling continue.
   - A dispatch paused before launch while `discard` returns its lease never starts a worker (`tests/dispatch/finish.test.ts`, "finding 1"), and a dispatcher whose attempt was resolved while it waited does not acquire a lease (`tests/dispatch/exclusion.test.ts`). Launch rows cannot be changed or removed (`tests/runtime/records.test.ts`).
   - No command calls `status` to find or classify an attempt (`tests/dispatch/observe.test.ts`, "finish, discard and prune do not depend on status-only reads or diagnostics").
   - Each safety check has tests of its permissions and refusals (`tests/dispatch/safety.test.ts`).
   - Confirmations are recorded in one form, naming their attempt, person, time and exact scope, and authorise only what they name (`tests/attempts/store.test.ts`).
   - **Not met:** see [Not yet met](#not-yet-met) for the step runner and the dispatcher loop. The task-store contract's rules are covered by the tests above, but they have not been mapped to tests one rule at a time.
2. **`finish` without `--no-processes`.** `tests/dispatch/finish.test.ts` finishes under `manual` and `local-merge` with the lease retained, then returns it with `--no-processes` without repeating any step. Tests interrupt each step and resume ("finish resumes … without process confirmation or repeating completed records"). A dependent task is not ready before the finish and is ready after it.
3. **Specifications and requests.**
   - A change to the title, instructions, repository, kind or acceptance criteria during acquisition holds the attempt as `task_definition_changed` with its unused lease and no launch (`tests/dispatch/specification.test.ts`). Changes after start leave the worker's input unchanged, and inspection after reopening shows the stored specification, not the new configuration.
   - A request repeated after archiving returns the original attempt and starts nothing, and a reused request ID with different inputs refuses as `request_input_mismatch` (`tests/dispatch/requests.test.ts`, `tests/dispatch/from-attempt.test.ts`).
   - A changed `result.json` cannot replace the recorded result (`tests/dispatch/finish.test.ts`, "recorded results keep the exact report and commit after the file is changed").
   - With Pi missing or broken, task commands, `status`, `finish` and `discard` still work (`tests/config.test.ts`).
4. **When an owner cannot be read.** `tests/dispatch/owner-reads.test.ts`, `tests/dispatch/owner-reads-remaining.test.ts` and `tests/dispatch/owner-read-commands.test.ts` inject failures for each operation and owner. A failure before any effect is retryable, keeps the failed command's output, and running again completes with each effect once. A failure after an effect's intent, or after the effect, requires reconciliation and never repeats the effect. `tests/dispatch/read-reconciliation.test.ts` covers the reconciliation itself.
5. **Acceptance criteria as data.** A task's criteria are stored in order and shown (`tests/tasks/commands.test.ts`), reach the worker in its prompt (`tests/dispatch/criteria.test.ts`: the synthetic worker builds its report from the criteria it was sent, and the report names them in order), and a result that does not report every criterion once, with its exact text and position, is held as invalid (`tests/dispatch/criteria.test.ts`, `tests/runtime/contracts.test.ts`).
6. **Starting from an earlier attempt.** `tests/dispatch/from-attempt.test.ts` starts at the exact recorded output, on a new branch and workspace, with an immutable handover. It is refused while the earlier worker might be running (`tests/attempts/starting-point.test.ts`), when the earlier output is not retained (`tests/dispatch/reserve.test.ts`), beyond the per-task attempt limit (`tests/attempts/starting-point.test.ts`), and beyond the objective's budget (`tests/dispatch/objective-budget.test.ts`).
7. **Checks and review.** Checks run without a shell at the exact output commit and are reused for that commit only (`tests/dispatch/checks.test.ts`). The supervisor's acceptance is refused unless every configured check and a passing review are recorded for the exact commit, while a person is not restricted (`tests/dispatch/caller-authority.test.ts`, `tests/dispatch/safety.test.ts`). A rebased commit needs fresh checks and review (`tests/dispatch/rebase.test.ts`). A review reporting another commit is never recorded against the reviewed attempt (`tests/dispatch/review.test.ts`).
8. **Caller identity and permissions.** `tests/dispatch/caller-authority.test.ts`: the host supplies the caller, and `--as` is only a recorded label; each permission is refused inside its operation before effects, including dry runs; only the creator changes an objective's authority; tasks outside the objective are refused; lease return is always a person's. `tests/supervise/cli.test.ts` shows that the restricted command refuses identity and objective overrides.
9. **Questions from workers.** A worker's question is recorded once and produces a `question_asked` event (`tests/runtime/questions.test.ts`, `tests/supervise/events.test.ts`). The answer reaches the worker between turns or while it runs (`tests/dispatch/questions.test.ts`). An open question survives its worker finishing and pruning, and its answer appears in the next attempt's handover.
10. **The supervisor.** The scripted part is met: a supervisor with three workers receives each worker's finish and question as events in the order they happen, and an event when one worker's dispatch process stops while the other two keep running (`tests/supervise/cli.test.ts`; the stale-heartbeat event's conditions are in `tests/supervise/events.test.ts`, each disabled in turn to confirm a test fails). The [real run in Pi](#the-real-run-in-pi) showed every part of the criterion except dispatching independent tasks together and a repair after a failed review; see [Not yet met](#not-yet-met).
11. **`finish --rebase`.** `tests/dispatch/rebase.test.ts`: a moved target refuses `finish` with a next action naming `--rebase` and changes nothing; a clean rebase integrates and records the original, rebased and target commits; a conflict, a dirty workspace (uncommitted or untracked files), commits beyond the result commit and merge commits are refused without changing the branch; a commit that becomes empty stops the rebase. A person's command line is their approval, and a supervisor needs the objective's rebase permission, including on dry runs. Interrupted rebases are recovered without rebasing again, and a second rebase replays only the attempt's commits.
12. **Several attempts at once.** `tests/dispatch/concurrency.test.ts`: with `maxAttempts` 2, two dispatch processes start different tasks and a third refuses at capacity; the default of 1 still allows one; racing dispatches start one attempt for one task, and automatic selection moves on while a named dispatch refuses; a fresh heartbeat, and a launch logged without a launch row, block only their own task; a missing, released, unreadable, stale, future-dated or invalid heartbeat blocks all dispatch, including while another worker's heartbeat is fresh; `status` text and JSON show capacity, active attempts and the blocking attempt, and an unreadable count as unknown. Continuations and reviews keep their task-scoped stopped-worker checks. The import refuses fresh heartbeats (`tests/tasks/import.test.ts`), and an objective budget stops only its own attempt (`tests/dispatch/objective-budget.test.ts`).
13. **Platforms.** The suite passes on macOS (above), and CI run 41837408902 for `e38d9d2` passed on Linux, macOS and Windows. See [CI](#ci).

## Not yet met

- **The step runner and the dispatcher loop (criterion 1).** The criterion requires `finish`, `discard` and dispatch's finalisation to run through the step runner, with a test for each showing that `--dry-run` plans the steps a run then takes, and `dispatch --once` to run through the dispatcher loop. Only `finish` uses the step runner (`src/dispatch/finish.ts`, `tests/dispatch/steps.test.ts`, and the dry-run tests in `tests/dispatch/rebase.test.ts` and `tests/cli.test.ts`). `discard` and dispatch's finalisation have dry runs, but not through the step runner, and there is no dispatcher loop: `dispatchOnce` runs one dispatch from start to finish. The PRD marks step 1 complete regardless. Either the criterion should be changed, or these should be done before Phase 4's background dispatcher, which is the main user of a dispatcher loop.
- **Two parts of the real run in Pi (criterion 10).** The supervisor planned two tasks, the second depending on the first, so it never had independent tasks to dispatch together. Parallel dispatch is covered by tests (criterion 12) and was used by hand during step 12, but not by a supervisor. All three reviews passed, so no repair after a failed review was needed. A second, shorter run with an objective that has independent parts would show the first; a failed review cannot be arranged without making the run artificial.

## The real run in Pi

On 4 November 2026 Nick gave a Pi supervisor the objective `status-readability`: make `switchboard status` useful in a context with many finished attempts, with five acceptance criteria and a budget of 40 (US dollars). The configuration was `switchboard.json` with `maxAttempts` 2 and two configured checks, `types` (`npm run check`) and `tests` (`npm test`). The supervisor and the workers used Pi 1.5.0 with `openai-codex` / `gpt-6.1-sol`.

What happened, in UTC:

- 13:02 Nick created the objective and started the supervisor with `switchboard supervisor start`. The supervisor read the briefing, wrote a plan in its notes and added two tasks: `status-readability-impl` (criteria 1 to 3 and the test for criterion 4) and `status-readability-docs`, blocked by the first.
- 13:04 It dispatched `status-readability-impl`. Within a few seconds the worker asked whether it could name the new option `--attention-only`; the supervisor answered with `sb_answer`, approving the name.
- 13:05 Nick quit the Pi session while the worker ran and started a new one. The new session (`8c883d55`) read the briefing and waited for events. It did not start the running worker again: the task has one attempt.
- 13:31 The worker finished. The supervisor created and dispatched a review, which passed at 13:42 for commit `ef91ccc`, with all five criteria met.
- 13:43 Finishing was refused because `main` had moved (Nick committed `e38d9d2` during the run). The supervisor finished with `--rebase`; both checks passed on the rebased commit `559dcfc`, and the finish was then refused because that commit had no review.
- 13:51 The supervisor's next three model calls failed with "Codex error: The usage limit has been reached", and it stopped. See [findings](#findings-from-the-real-run).
- 20:50 After the provider limit reset, Nick typed a message into the supervisor's Pi session asking it to review `559dcfc`, finish and continue. The supervisor dispatched the review, which passed, and finished: `main` moved to `559dcfc`.
- 20:58 It dispatched `status-readability-docs`. The worker finished at 21:10, the review passed at 21:21, both checks passed, and the supervisor finished it (`3d436fc`) at 21:26.
- 21:26 The supervisor completed the objective with a statement for each criterion.

Results:

- Three commits on `main`: `7958641`, `559dcfc` and `3d436fc`. A person still returned the leases and removed the review attempts afterwards, because the supervisor cannot return a lease.
- Spending recorded against the objective: $2.11 ($1.16 workers, $0.95 supervisor). About $0.07 of supervisor usage after completion was refused and not recorded; see findings.
- The supervisor sessions called only Switchboard tools: `sb_briefing` (13 times), `sb_dispatch` (6), `sb_finish` (4), `sb_review` (3), `sb_note` and `sb_task_add` (2 each), and `sb_answer`, `sb_task_block`, `sb_task_show`, `sb_task_update`, `sb_objective_show` and `sb_objective_complete` (1 each). `switchboard supervisor start` launches Pi with `--no-extensions`, `--no-skills`, `--no-context-files` and `--tools` naming only these tools, so the session had no shell, editing or file-writing tools.
- **Interventions: one**, the message at 20:50 after the provider error. Quitting and restarting Pi at 13:05 is part of the criterion's test, not counted as an intervention.

### Findings from the real run

- **A provider error stopped the supervisor silently.** Pi recorded the failed replies with `stopReason: "error"`, but the extension had already acknowledged the events it delivered, so no later event arrived, and `status` and the briefing showed nothing wrong for seven hours. Task `supervisor-stopped-on-error` records the stopped session and shows it as needing attention. A later task may add optional bounded retries.
- **Usage after completion was refused.** Once the objective was completed, every usage report failed with "Supervisor usage reporting failed", and an event fetched before completion was delivered afterwards. Fixed in `84e0df0` and `c26b04b`. The extension recognised closure by matching refusal text; task `supervisor-closed-refusal-code` gives the refusal its own code.
- **A rebase needs a second review.** A commit on `main` during the run meant the reviewed commit had to be rebased, and the rebased commit needed its own review, as criterion 7 requires. This cost one extra review. Whether a review should still count after a clean rebase whose checks pass is a design question for later.
- **The supervisor ends turns with no text** while it waits for events, so the Pi session looks blocked to a person watching it.

## CI

CI run 41141491092 for `f787f2a` passed on macOS and failed on Linux and Windows. Both causes were in the tests, not in Switchboard:

- `tests/dispatch/rebase.test.ts`, "the CLI accepts --rebase and uses the person's existing approval" (Linux and Windows): the test started the command without the fixture's Git identity, and the CI hosts have none, so Git refused to write the rebased commit. The test now passes the fixture's environment. It was reproduced on macOS by hiding the host's Git identity, and passes there with the fix.
- `tests/dispatch/questions.test.ts`, both "a worker's question is polled and its answer reaches it" tests (Windows): the prompt quotes the questions directory as JSON, which doubles Windows backslashes, and the test looked for the unquoted path. The test now looks for the quoted path. This fix is checked only by CI on Windows.

CI run 41837408902 for `e38d9d2` (4 November 2026) passed on Linux, macOS and Windows.
