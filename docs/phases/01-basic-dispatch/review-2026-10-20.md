## Critical

### 1. Staggered dispatches can acquire two leases and launch two workers for the same task

**Location:** `src/dispatch/dispatch.ts:125–162`; `src/attempts/log.ts:97–108`; `tests/dispatch/faults.test.ts:113–119`.

**Scenario:** Dispatcher A creates attempt 1 and pauses before acquisition has become visible. B now inspects the log and sees attempt 1, but no lease, runtime binding, or in-flight task. The `blocked` predicate does not consider unfinished attempts. B deliberately creates attempt 2 using `previous = 1`. Both can then acquire different output branches. If both readiness reads precede their starts, both launch. The exclusive directory rename only prevents contenders for the **same attempt number**.

**Evidence:** An executed, barrier-controlled probe paused A at acquisition, started B after A's `requested` entry existed, and allowed both readiness checks before completing their starts. With real `AttemptLog`, `RuntimeRecords`, and `dispatchOnce`, and fake task/workspace adapters, the result was:

```json
{"acquisitions":2,"launches":2,"attempts":2}
```

No agents were launched: `launches` counts calls to a recording runtime stub. The ordering is consistent with the real adapter: tasks-axi start is not readiness-conditional, and the existing Treehouse test proves it allows multiple leases with one holder. The current concurrency test starts both invocations together and only covers the schedule where they contend for attempt 1.

This contradicts PRD acceptance criterion 7 and ADR-0006's claim that two invocations cannot dispatch the same task “whatever their timing.” Concurrent dispatch is unsupported, but the PRD **explicitly retains this safety guarantee** even in that case.

**Fix:** Make eligibility depend on the preceding attempt being conclusively finished/resolved, and atomically claim the task before acquisition. Preserve an unresolved acquisition intent as a blocking fact. Add deterministic staggered tests, not just simultaneous `Promise.all` starts.

## High

### 2. Request IDs are not claimed atomically across tasks

**Location:** `src/dispatch/dispatch.ts:108–110,157–162`; `src/attempts/log.ts:164–166`.

**Scenario:** Two invocations with the same request ID both finish `findByRequest` before either creates its requested entry. If they select different tasks, their per-task exclusive creations do not conflict. One logical request starts two attempts; later lookups return whichever match appears first.

**Evidence:** Executed probe synchronized the two initial lookups and dispatched two explicit ready task IDs with one request ID. The real log contained:

```json
[{"task":"one-a1","request":"same-request"},{"task":"two-b1","request":"same-request"}]
```

This is separate from finding 1: fixing same-task exclusion does not make a context-wide request ID unique. Current repeat-request tests repeat only after the first invocation has recorded the request.

**Fix:** Exclusively reserve a context-scoped request ID and bind it to one attempt, with conservative handling of incomplete reservations. Reject or return the existing binding on every competing call.

### 3. A crash after acquisition but before logging it defeats old-pool protection

**Location:** `src/dispatch/dispatch.ts:93–99,182–196`; `tests/dispatch/crash.test.ts:36–48`; `tests/dispatch/pools.test.ts`.

**Scenario:** Treehouse creates a lease; the dispatcher dies before appending `leased` or `halted`. The log contains only `requested`, including the original pool. The operator then adds/changes `origin`. Treehouse lists the new pool, and the old lease disappears from that inventory. `leasesInOtherPools` ignores the requested pool unless a `halted/outcome_unknown` entry exists. The still-ready task is eligible for another lease.

**Evidence:** The existing after-lease crash test explicitly establishes this requested-only state. An executed probe supplied that state with a different current pool: `leasesInOtherPools` was `[]`, and explicit dry-run selection returned `dry_run`. Pool tests cover lost replies followed by a logged halt, not a crash that cannot write one.

**Fix:** Treat a requested acquisition with no conclusive refusal/terminal observation as potentially acquired in its recorded pool. Do not require a crash to have written an error entry. Add the combined crash-and-origin-change test and make task-based lease-return resolution available for this state.

### 4. `resolve --worker-stopped` can succeed immediately before the dispatcher launches

**Location:** `src/dispatch/dispatch.ts:219–234`; `src/dispatch/resolve.ts:27–42`; `src/runtime/pi/worker.ts:68–72`.

**Scenario:** The dispatcher appends `launched`, then stalls before runtime reservation/heartbeat creation. `resolve` finds a possibly-running attempt but no runtime heartbeat. The operator can truthfully observe that no worker exists and confirm it stopped. `resolve` appends `operator_resolved` and reports success. The original dispatcher resumes and launches anyway; neither launch nor reservation checks the resolution.

**Evidence:** Executed probe paused the launch callback after the real `launched` entry, called `resolveStopped(...confirmed:true)`, and then released launch. Output:

```json
{"resolution":"resolved","launchedAfterResolve":true,"runtimeChild":"unknown"}
```

There was no real worker; the callback reserved runtime records. This is a race between supported commands, not an external task-state writer. The resolution also removes the log-based dispatch blocker during the window.

**Fix:** Coordinate stop confirmation with launch ownership, not just a diagnostic heartbeat. A confirmation must fence a pending launch, or be refused while the dispatcher still owns permission to launch. Test this pre-binding window and a paused/stale dispatcher resuming after confirmation.

### 5. Different-kind concurrent appends corrupt the attempt log

**Location:** `src/attempts/log.ts:120–122,168–176,179–195`; `docs/phases/01-basic-dispatch/attempt-log.md`, “Appending.”

**Scenario:** Two writers read N entries. One writes `00NN-operator_request.json`; another writes `00NN-worker_finished.json` or `00NN-operator_resolved.json`. Since the final names differ, both hard links succeed. Readers reject the duplicate sequence, and all subsequent inspections of the context fail. Cross-process resolution and dispatcher writes can overlap; request logging and finalisation also need serialization.

**Evidence:** Executed probe synchronized two `append` calls after their reads, using different entry kinds. Both promises fulfilled; the following real `read` failed with **`Uninspectable attempt entry sequence`**. Thus the documentation's claim that a second writer at the same sequence fails is false for different kinds.

**Fix:** Claim the sequence with a kind-independent filename, or serialize all writers with a cross-process append mechanism. Define bounded conflict handling. Use the same append path for dispatcher, control, and resolution events, and test different-kind races.

### 6. A dangling artefact symlink is reported as retained

**Location:** `src/workspaces/retention.ts:89–94`.

**Scenario:** A required report is an absolute symlink outside the workspace whose target is missing. `lstat` succeeds. `realpath` fails, but the catch substitutes the original outside path. No finding is recorded, so an independent-deliverable task can become done without a readable report.

**Evidence:** Executed `checkRetention` against a clean/read-only repository with a temporary dangling report symlink. Result: **`retained: true`, `findings: []`**. The missing-file test only covers a nonexistent directory entry, not an existing broken link.

**Fix:** Treat resolution/stat/read failures as non-retention. Require the expected artefact type and a resolvable retained target, or disallow symlinks. Add dangling-link and inaccessible-target tests.

### 7. Required Git deliverables other than the first output-branch reference are never retained-checked

**Location:** `src/runtime/contracts.ts:67–78`; `src/dispatch/dispatch.ts:240–241,261–266,358–360`.

**Scenario:** An artefact contract requires a deliverable named `report`. The result supplies `report` as a Git reference to a nonexistent branch/commit, plus an unrelated, existing artefact named `extra`. Validation checks the names and that *some* artefact exists. Finalisation checks artefact paths and only the first Git reference matching the configured output branch. The actual required `report` is unchecked. Code contracts have the analogous problem with additional named Git references or multiple commits on the output branch.

**Evidence:** Executed probe used real `validateWorkerResult`, dispatch, log, and retention checking, with a fake task store. Required `report` pointed at branch `does-not-exist` and commit `cccc…`; only `extra` existed. Dispatch returned **`done`**.

**Fix:** Resolve required names to explicit deliverable types, and retention-check every required Git branch/commit and artefact. Reject incompatible reference kinds rather than allowing an unrelated artefact to satisfy an artefact contract.

## Medium

### 8. Storage containment protects only against the current workspace, not other recyclable workspaces

**Location:** `src/config.ts:28–30`; `src/runtime/records.ts:132–137`; `src/attempts/log.ts:215–224`; `src/workspaces/retention.ts:88–94`.

**Scenario:** Configure `runtimeRoot` inside an earlier leased workspace A, then dispatch into workspace B. Reservation checks whether the root is inside B, so it accepts this configuration. The attempt log, results, and sessions can be destroyed when A is returned. Similarly, B's required report can be placed in A and pass retention because it is outside B.

**Evidence:** Source inspection: configuration validates absoluteness, attempt logging has no workspace containment check, and both runtime/retention containment predicates compare only one workspace. This contradicts the configured root's “outside every workspace” requirement and the promised retained artefact directory. No destructive return was run.

**Fix:** Validate runtime storage against the provider's recyclable area before writing any attempt. Constrain retained reports to the assigned artefact directory or another explicitly qualified storage location; do not infer retention solely from being outside the current workspace.

### 9. Unknown final task updates are confirmed without confirming their evidence

**Location:** `src/dispatch/dispatch.ts:271–291`; compare `src/tasks/tasks-axi.ts:95–98,105–120`.

**Scenario:** A final update throws because the intended outcome/evidence was not fully retained, but readback shows `done`, or queued+held with the expected reason. Dispatch treats that as the complete intended update and appends `task_recorded`, even if the attempt summary, evidence, and work references are missing. This weakens the adapter's stricter body/note check.

**Evidence:** Executed fault probe made `recordDone` leave state `done` but not its note, then throw. Readback body remained just `instructions`; dispatch returned **`done`**. Existing final-update fault tests use an entirely applied update or an entirely unapplied one, not incomplete evidence retention. The investigation mapping explicitly requires comparing the complete expected outcome, not just state.

**Fix:** Use the same complete expected-outcome predicate for normal adapter readback and uncertain-update reconciliation. A missing note/body must result in `complete_task_update`, not confirmed completion.

### 10. Repeated requests report historical lease facts instead of inspecting owners

**Location:** `src/dispatch/dispatch.ts:108–110,313–323`.

**Scenario:** Repeat a recorded request after its lease has been returned, its pool has changed, or the workspace/runtime owner has become unreadable. The early-return path reads only the task. Presence of a lease ID in the log becomes `lease: preserved`; absence becomes `none`, even for an unknown acquisition.

**Evidence:** Executed probe supplied a logged lease and a workspace adapter whose inventory throws. Repeating the request still reported **`lease: preserved`** without attempting that inventory. A requested-only crash would instead report `none` even if Treehouse holds its lease. PRD “Repeated requests” requires owner inspection as `status` does.

**Fix:** Keep deduplication before side effects, but derive the replay report from common owner inspection. Preserve `unknown` and report actual runtime liveness and current pool/lease state. Add replay tests with returned, hidden, and unreadable leases.

### 11. A confirmed child exit is overridden by an unfinished log entry

**Location:** `src/dispatch/dispatch.ts:78–90`; `src/runtime/pi/worker.ts:157–158`.

**Scenario:** The runtime writes `child-exit.json`, then the dispatcher crashes before appending `worker_finished`. Inspection correctly discovers the observed exit, but its second loop adds the attempt back to `possiblyRunning` solely because the log lacks `worker_finished`. All work is blocked until the operator makes a redundant stop confirmation.

**Evidence:** Executed probe created a matching binding and exit receipt, and a log ending at `launched`. It returned **`runtime: exited`, `possiblyRunning: 1`**. This contradicts runtime ownership of liveness and the rule that a stopped attempt blocks only its own task.

**Fix:** Use the log fallback only when no matching conclusive runtime observation exists. Test a crash between the exit receipt and the worker-finished append.

### 12. `status` can say “clear” when a task is unreadable or orphaned in flight

**Location:** `src/dispatch/status.ts:76–87,104–110`.

**Scenario:** An attempt has no currently listed lease, and its individual task read fails. The task is labelled `unreadable`, but the no-lease branch chooses `nextAction: none`; overall status becomes clear. Separately, an in-flight task with no log/runtime/lease is printed in `inFlight` but never contributes to `attention`.

**Evidence:** Executed probe with a requested attempt and failed individual task read returned **`ok: true`, `reason: clear`, `task: unreadable`, `nextAction: dispatch_again`**. The orphan-in-flight omission follows directly from the attention expression.

**Fix:** Unknown task state and unaccounted in-flight tasks need explicit attention and inspection actions. Test list operations succeeding while individual task reads fail.

### 13. Takeover instructions are offered after the workspace has been returned or reassigned

**Location:** `src/dispatch/status.ts:32–43,75–92`.

**Scenario:** A worker exits; the operator returns its lease; Treehouse reuses that path for another task. The old attempt's runtime binding remains, and `status` still recommends opening its Pi session **in the recorded old workspace path**. That path can now belong to another worker/task. The command also interpolates the session directory without shell quoting, so ordinary paths containing spaces do not work as printed.

**Evidence:** Source inspection: `workerView` receives only runtime state and `possiblyRunning`; the caller has computed `leaseHeld` but does not pass it. The takeover expression checks only that the old worker is not possibly running. The command string quotes neither directory.

**Fix:** Offer workspace takeover only after confirming the current lease ID, holder, and path still match. Otherwise offer transcript inspection or explicit reacquisition guidance, not execution in a stale path. Provide correctly quoted platform-specific commands.

### 14. Runtime availability is not checked at preflight

**Location:** `src/config.ts:41–44,75–87`; `src/runtime/pi/worker.ts:21–23`; `src/dispatch/dispatch.ts:182–234`.

**Scenario:** `worker.piEntrypoint` names a missing/unreadable file. Configuration/dependency creation succeeds because it is only checked for being absolute. Dry run can report an eligible task, and real dispatch acquires a lease and marks the task in flight before Node fails to load the entrypoint. This predictable configuration error becomes a failed worker and held task.

**Evidence:** Source inspection: neither dependency creation nor preflight stats/opens the entrypoint. The actual executable is the already-running Node binary, so a missing Pi module is discovered only in the spawned process. PRD step 1 and `createDependencies`' own comment promise adapter availability validation before dispatch.

**Fix:** Check the configured entrypoint's existence/readability and the supported runtime capability/version before creating an attempt or acquiring a lease. Keep uncertain-spawn compensation for genuinely runtime failures.

### 15. Post-acquisition storage failures escape as stack traces, even with `--json`

**Location:** `src/dispatch/dispatch.ts:193–196,210,219,243–249,268,291`; `src/cli.ts:151–164`.

**Scenario:** Acquisition succeeds, then a later attempt-log append fails, for example because storage fills or an append conflicts. The exception is not converted to a structured stopped report. The CLI prints a stack trace to stderr and exits 2; JSON stdout has no result identifying the retained lease and failed stage. Runtime/retention exceptions can take similar paths.

**Evidence:** Source inspection: initial attempt creation has a refusal catch, but these subsequent awaited appends do not. The outer CLI catch is a generic exception printer. Fault tests inject owner failures, not these post-side-effect journal failures. The PRD promises a structured result/refusal with observed state and a concrete next action.

**Fix:** Put a side-effect-aware error boundary around each dispatch stage. Preserve known identifiers and classify the outcome as stopped/unknown; do not call a post-acquisition failure a usage/configuration error. Add disk/write/conflict failures after every persisted boundary.

### 16. Recognized options for the wrong command are silently ignored

**Location:** `src/cli.ts:43–50,63–95,110–118`.

**Scenario:** `stop --lease L --dry-run` is accepted and sends a real stop request; `--dry-run` is parsed globally but never checked for validity on `stop`. Other dispatch-only or resolve-only options are similarly accepted on unrelated commands. A caller's attempted non-mutating command can mutate the running attempt instead of failing usage validation.

**Evidence:** Source inspection of the global option table and command branches. Only a few combinations, especially `--attempt`, are rejected. The “invalid options” test covers unknown options/type errors, not recognized options on the wrong command.

**Fix:** Validate a command-specific option allowlist before loading configuration or making changes. In particular reject `--dry-run` everywhere it is not implemented. Add wrong-command tests for every mutating command.

### 17. Subprocess timeouts do not bound pipe lifetime

**Location:** `src/infra/command.ts:22–33`; `src/runtime/pi/rpc-client.ts:45,56–64`; `src/runtime/pi/worker.ts:184–191`.

**Scenario:** An external command spawns a descendant that inherits its stdout/stderr. Killing or observing exit of the direct child does not close those inherited pipe writers. `runCommand` waits for `close`, not just `exit`, and its timeout only kills the direct child. It can therefore wait indefinitely past its deadline. The RPC path bounds the wait for `closed`, but leaves the pipe handles open after that timeout, so the foreground Node process can still be kept alive.

**Evidence:** Source inspection and Node's distinction between child exit and stream closure. Neither path destroys/unrefs the pipes on its terminal timeout. This is relevant to Git hooks and tool subprocesses; no descendant-process reproduction was run, to avoid creating background processes during this review.

**Fix:** Separate direct-child exit observation from bounded output draining. After the drain budget, report the correct failure/unknown outcome and release local stream handles without claiming descendants terminated. Bound captured command output as well: the current infrastructure accumulates it without a byte limit.

### 18. The worker test suite does not protect ambient context-file isolation

**Location:** `src/runtime/pi/worker.ts:253`; `tests/runtime/worker.test.ts:20–39`; `docs/phases/01-basic-dispatch/runtime-integration.md`, “Real Pi run.”

**Scenario:** A future edit removes `--no-context-files`. Pi again loads the operator's global/project context instructions, despite the worker isolation contract. The normal tests still pass because the synthetic peer does not load context files, and the startup test does not assert this flag.

**Evidence:** **Mutation executed:** removed only `--no-context-files`, ran the entire `tests/runtime/worker.test.ts`, and obtained **45 passed, 0 failed**. Restored immediately. The runtime notes document that this exact omission already contaminated a real worker's system prompt once.

**Fix:** Assert the complete safety-relevant startup flag set and required arguments. Add a non-model Pi startup/configuration probe against deliberately conflicting context/settings files when feasible. Do not describe the synthetic peer as proving ambient configuration isolation.

## Additional concerns not confirmed end to end

These are not presented as reproduced production failures:

- **Control forwarding at shutdown:** `src/runtime/pi/worker.ts:87–110,169–183` starts asynchronous forwarding from an interval, but clears the timer without awaiting an in-flight forwarding operation. It also swallows result-file failures and dispatcher hook errors; dispatch's hook swallows append failures (`dispatch.ts:228–232`). A late acknowledgement or slow filesystem could lose the promised attempt-log record or race finalisation. The append collision mechanism itself is confirmed in finding 5; a full late-steering reproduction was not run. Track/drain the forwarding promise and expose failed audit recording.
- **Any thrown launch error is called “not started”:** `dispatch.ts:235–238` does not inspect runtime identity before finalising a rejected launch promise. Current Pi code catches most post-spawn failures, but `shutdown`, hooks, or a future adapter can throw after spawn. I did not induce a production Pi post-spawn rejection with an unobserved child. The launch interface should distinguish definite no-child failure from an uncertain exception.
- **Large result/task text versus OS argument limits:** result files may approach 1 MiB, while task evidence is copied into `--note`/`--body` arguments (`tasks-axi.ts:97,113`). Linux's per-argument and Windows' command-line limits are much smaller. This was not executed on those hosts. Bound inline task notes and retain larger evidence by reference or use a supported file/stdin input.
- **Base verification:** `TreehouseProvider.verify` checks branch and parses HEAD but receives no expected base commit (`treehouse.ts:69,99–113`). The real happy-path test verifies the expected starting commit externally. I did not make Treehouse return a wrong-base allocation, so I have not claimed that current Treehouse misallocates. Requalify this boundary when fetch/hooks/provider versions change.
- **Heartbeat timing:** fresh heartbeats deliberately refuse stop confirmation; stale/missing heartbeats are not proof a dispatcher is dead. The concrete pre-launch race is finding 4. Wider suspend/resume, clock-change, and host-failure schedules were not reproduced.
- **Host power loss and hostile same-user modification:** not tested. Files are synced but parent directories are not qualified for power-loss persistence. The documentation explicitly excludes protection against malicious same-OS-user workers; I did not misclassify that acknowledged lack of a sandbox as a new defect.

## What was checked and found sound

Read completely: `README.md`, principles, architecture, **all six ADRs**, **every file under `docs/phases/01-basic-dispatch/`**, **all `src/` and `tests/` files**, root package/compiler/ignore settings, CI configuration, the real-dispatch demo, and the historical investigation source/test programs. Inspected the installed Pi CLI option documentation to check the session-takeover flag semantics; `--session-id` itself is supported, so that is not a finding.

Within the exercised boundaries:

- Production workspace operations expose acquire/inspect only; no production `src/` path returns a lease. Failure compensation preserves leases. Descendant termination is explicitly unverified rather than treated as return authority.
- Worker result parsing is bounded, strict, versioned, and checks full context/task/lease/session identity. Symlinked result JSON is refused. Worker completion remains separate from task acceptance.
- Review-required completed code is held, not marked done; independent retained deliverables can become done.
- Result commits on the principal output branch are ancestry-checked from the backing repository. Dirty/untracked files and orphan commits prevent ordinary code retention; scratch workspace findings remain diagnostic for artefact contracts.
- The tested authoritative tasks-axi addressing resists cwd, environment, and config redirection. Held work and its dependants stay excluded from readiness.
- The runtime reserves one directory per context/lease, refuses reuse, installs event observation before the single prompt, does not retry lost prompt acknowledgements, and separates idle/settled state from observed direct-child exit.
- LF framing, UTF-8 split handling, malformed protocol rejection, abort escalation, provider-error reporting, and most identity/lifecycle fault cases have meaningful assertions.
- Write-once JSON files are published by hard-linking complete flushed temporary files; readers do not consume partially published contents. The defect is sequence ownership across differently named entries, not replacement of an individual write-once file.
- Stop/steer request claims exclude forwarding after a sender has successfully withdrawn a request. Heartbeats are diagnostic and missing/stale ones do not themselves authorize dispatch.
