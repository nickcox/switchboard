## Critical

### 1. `discard` can return an unfinished dispatcher's lease and then let that dispatcher launch

**Severity:** critical  
**Location:** `src/dispatch/state.ts:53–64`; `src/dispatch/finish.ts:148–176`; `src/dispatch/dispatch.ts:251–279`.

**Scenario:** Dispatch has acquired and logged a lease and checked readiness, but pauses inside `tasks.start`, before launching. There is genuinely no worker process yet. `status` labels the open leased attempt `stopped`: the `unfinished` case applies only when there is *no* lease. `discard --confirm --no-processes` accepts `stopped` and returns the lease. The original dispatcher resumes and proceeds to launch against the returned workspace. Neither the discard nor the subsequent launch establishes a fence against this pending launch.

**Executed evidence:** A barrier held `tasks.start` before its mutation, then the real `discard` returned the disposable Treehouse lease. After releasing the barrier, the launch stub was called while the provider listed zero leases:

```json
{"state":"stopped","discard":"discarded","held":false,"launchedAfterReturn":true}
```

No actual worker was launched in this probe. The production dispatcher would call its normal runtime at precisely that point. A recycled path can already belong to another allocation. The operator's process confirmation is insufficient here even when truthful: it does not cancel a future launch. Holding the queued task alone is not a complete fix either; a dispatcher can instead be paused after its start mutation/readback but before returning from that call.

**Suggested fix:** Distinguish an actively open leased attempt from a halted attempt. Coordinate discard with dispatch ownership and durably fence any pending launch before releasing its lease. Make launch validate the same ownership/fence atomically, including the pre-runtime-reservation window. Add deterministic tests pausing on both sides of `tasks.start` and before runtime reservation.

## High

### 2. Ordinary `finish` omits the retention check immediately before return

**Severity:** high  
**Location:** `src/dispatch/finish.ts:81–85, 123–142`.

**Scenario:** A normal worker-result finish passes retention, then integrates and/or updates the task. An artefact disappears, or a retained ref changes, during those intervening operations. The final retention check runs only inside `if (acceptedCommit)`, so ordinary finish returns the lease using the earlier observation. This also affects ordinary retries after a partial failure.

**Executed evidence:** Added a reported artefact in the assigned artefact directory to a completed fixture result. The task-store wrapper removed it while recording done. Ordinary finish returned successfully:

```json
{"reason":"finished","checks":1,"artefactExists":false,"leases":0}
```

Treehouse's dirty-worktree refusal does not check retained artefacts or prove result commits remain on the promised refs. PRD “Returning a lease” condition 2 requires the immediate recheck on **both** worker-result and accepted-output paths. The current accepted-output-only test does not cover this path.

**Suggested fix:** Invoke the existing `check` closure unconditionally immediately before returning. Record/report that latest result, and refuse if it fails or cannot run. Add ordinary-result tests that remove an artefact or move a retained ref during integration/task recording, not only tests that dirty the workspace.

### 3. A tag named like the base branch can make worker output authoritative policy

**Severity:** high  
**Location:** `src/dispatch/policy.ts:91–103`, especially `const object = \`${sources.baseRef}:${repositoryPolicyPath}\``.

**Scenario:** Configuration uses the normal `baseRef: "main"`. Main contains a manual policy. Another commit on the output branch contains a local-merge policy, and a tag named `main` points to that output commit. Git resolves the ambiguous unqualified name to the tag for the object lookup; Switchboard reads the output policy despite the base branch being unchanged. Tags are shared between Git worktrees.

**Executed evidence:** Created precisely those commits and the tag in a disposable repository, then called real `resolvePolicy`:

```json
{"kind":"local-merge","baseUnchanged":true}
```

This violates PRD line 79's explicit guarantee that policy changes take effect only after merging into the base branch. It is not a claim that a hostile same-user worker is sandboxed, nor that global/context forbids can be bypassed: those forbids still apply. It is a defect in the promised Git-reference provenance check.

**Suggested fix:** Resolve the explicitly qualified base-branch ref (`refs/heads/main`, appropriately normalised and validated), pin its commit, and read policy from that commit. Do not let Git's generic revision-name precedence select the authority. Test conflicting tags as well as ordinary output/worktree edits.

### 4. Concurrent prune resumptions can release a new request-ID reservation

**Severity:** high  
**Location:** `src/attempts/prune.ts:117–141`, especially `133–136`.

**Scenario:** Cleanup A reads the old reservation and checks that no visible attempt references it, then pauses. Cleanup B of the same tombstone completes and removes that reservation. A dispatcher reserves the now-free ID for new work. A resumes and unlinks the pathname based on its stale `current` value and stale lookup. The equality comparison is not conditional deletion of the actual current file.

**Executed evidence:** Used real `AttemptPruner` and `AttemptLog`, with a barrier after A's request lookup, B's complete cleanup, and a newly reserved/created attempt before releasing A:

```json
{"newAttemptStillExists":true,"reservationClaimedAgain":true}
```

The probe proves release of a reservation whose new attempt still exists, contrary to PRD criterion 6. Existing attempt lookup still deduplicates an already visible new attempt; it does **not** repair the reservation-before-attempt-creation window. In that window the same schedule permits another caller to claim the ID and create a different task's attempt while the first new caller is still creating its own. That extension follows from `dispatch.ts:184–202`; it was not a second end-to-end dispatch probe.

The existing reused-ID test is sequential: it replaces the reservation *before* cleanup reads it, so it does not cover the race.

**Suggested fix:** Serialize cleanup ownership and reservation release across processes, or use a generation/identity-conditional retirement scheme that cannot unlink a replacement. Ensure completed tombstones cannot be concurrently replayed by an already-running cleanup. Add the barrier-controlled schedule, including a new reservation whose attempt has not yet been published.

### 5. A rejected lease return becomes success if inspection has moved to another pool

**Severity:** high  
**Location:** `src/workspaces/treehouse.ts:74–85`.

**Scenario:** The repository's origin changes between finish/discard inspection and return. Treehouse refuses the return–for example because the workspace is dirty–but `leases()` now lists the new, empty pool. `listed === false` returns success before checking the return failure. Absence from a different pool is treated as proof of return.

**Executed evidence:** Acquired a real disposable lease, created an untracked file, changed origin, then called real `returnLease(..., {discardChanges:false})`. It resolved successfully. Removing the fixture origin to inspect the original pool showed the lease still held:

```json
{"reportedSuccess":true,"stillHeld":true}
```

This directly exercises the adapter, not a whole finish invocation. A fresh finish begun after the pool change would normally refuse; the supported-command failure is the change **between** its initial inspection and the return/readback. The caller can record `lease_returned` and report `lease: none` despite the refusal.

**Suggested fix:** Bind return/readback to the expected pool/allocation and inspect the actual returned path where necessary. A changed pool or failed/uncertain return whose allocation cannot be inspected must remain unknown, not success. Retain identity/holder preconditions.

### 6. Failed worktree discovery silently authorises a raw update of a checked-out branch

**Severity:** high  
**Location:** `src/workspaces/integration.ts:28–35`.

**Scenario:** `git worktree list --porcelain` fails or produces incomplete output. Its exit status, timeout and truncation are ignored. Empty output is interpreted as “target is not checked out,” and `update-ref` advances it without updating the target worktree/index. The final branch-head readback succeeds, so integration is reported successful.

**Executed evidence:** In a real fixture repository with main checked out and a strict descendant output commit, a Git shim failed only the worktree-list command and delegated everything else to real Git:

```json
{"refAdvanced":true,"fileExists":false,"status":"D  output.txt"}
```

The new file existed in the integrated commit but not the backing worktree; the index now represented a staged deletion. The command reported no integration error. Whole finish was not run in this probe; its call to this function would receive success.

**Suggested fix:** Validate discovery success and completeness before any mutation; distinguish unknown checkout state from an absent checkout. Refuse on failed, timed-out, truncated or malformed inventory. Test this boundary separately from non-fast-forward rejection.

## Medium

### 7. An unreadable policy blob is silently treated as a missing policy layer

**Severity:** medium  
**Location:** `src/dispatch/policy.ts:93–99`.

**Scenario:** The base commit exists, but a committed policy blob is unavailable/corrupt. Any nonzero `cat-file -e base:path` result followed by a successful base `rev-parse` is treated as “file absent.” Switchboard silently falls back to another layer or manual rather than reporting the unreadable repository policy.

**Executed evidence:** Committed a local-merge policy in a disposable repository, removed only its loose blob object, then resolved policy:

```json
{"kind":"manual","sources":{"kind":"default"},"forbidden":[]}
```

This is a storage-failure probe, not a hostile-worker isolation claim. A valid commit name does not prove the referenced tree/blob is readable. It contradicts the rule that an invalid/unreadable layer is an error and unknown is not absence.

**Suggested fix:** Inspect the pinned base tree to establish genuine path absence; if an entry exists, failure to read its object must be fatal. Test missing/corrupt tree and blob objects as well as missing paths and malformed JSON.

### 8. Fixing retained output does not make a `not_retained` attempt finishable

**Severity:** medium  
**Location:** `src/dispatch/state.ts:59`; `src/dispatch/finish.ts:58–61`.

**Scenario:** Dispatch holds a valid completed result because its retention check fails temporarily. The operator fixes the branch/artefact. The classification remains `not_retained` solely because of the historical hold-reason suffix. Both ordinary finish and `--accept-output` reject that state before checking the repaired work.

**Executed evidence:** Dispatched a real completed fixture with an injected initial retention failure, then used the normal retention implementation for finish. All actual output was retained, but finish returned:

```json
{"state":"not_retained","reason":"refused"}
```

The detail states that only awaiting-review/awaiting-finish or held-with-accept-output states are accepted. PRD guidance and `fix_or_discard` tell the operator to fix the output, but provide no supported transition that recognises that fix.

**Suggested fix:** Permit re-evaluation of a stopped, known, leased not-retained attempt under its original contract. Only advance it once fresh result/retention checks establish eligibility; do not require manually disguising its hold reason as review-required.

### 9. Completing an unconfirmed task update does not clear `task_update_unconfirmed`

**Severity:** medium  
**Location:** `src/dispatch/state.ts:55–61`; `src/dispatch/finish.ts:60–61`.

**Scenario:** Dispatch logs a finalisation halt without `task_recorded`. The operator follows the prescribed next action and completes the task-store update. Classification still returns `task_update_unconfirmed` from the old log before inspecting the current done state. Finish refuses, including with `--accept-output`.

**Executed evidence:** Failed the fixture's final hold update, then successfully called the real task store's `recordDone` as an operator repair:

```json
{"state":"task_update_unconfirmed","reason":"refused"}
```

The PRD state table explicitly says “Complete the update, then finish.” There is no supported reconciliation that records the now-confirmed outcome.

**Suggested fix:** Reconcile the intended outcome/evidence against the task owner's current record and append confirmation when established. Do not merely equate any done state with the intended update, but also do not permanently prefer the old failure over repaired owner evidence.

### 10. Successfully returned leases become unknown again after an origin change

**Severity:** medium  
**Location:** `src/dispatch/dispatch.ts:105–110, 442–453`; `src/dispatch/prune.ts:28`.

**Scenario:** Finish successfully returns a lease and records `lease_returned`. Later the operator adds/changes origin. `possibleLeasePool` still returns the old leased pool, and inspection recognises only `operator_resolved(action: lease_returned)`, not the actual `lease_returned` event. A conclusively finished attempt becomes an other-pool uncertainty. Prune also rejects its old pool unconditionally.

**Executed evidence:** Finished a real fixture normally, then added an origin:

```json
{"before":"finished","after":"lease_in_other_pool"}
```

Status requests a redundant operator confirmation; redispatch of a reopened task and pruning can remain blocked. This is not evidence of a newly acquired hidden lease.

**Suggested fix:** Carry conclusive return observations into the possible-lease/pool assessment, while still refusing genuinely unresolved acquisitions. Apply the same rule to pruning, with tests for both finished and unresolved attempts across a pool change.

### 11. Discard leaves an unheld queued task ready instead of holding it

**Severity:** medium  
**Location:** `src/dispatch/finish.ts:162–173`.

**Scenario:** Acquisition succeeds but task start is refused, leaving a leased, stopped attempt and a queued unheld task. Discard returns the lease but only invokes `recordHold` for `in_flight` tasks. The task becomes immediately dispatchable without the hold promised by the command and PRD.

**Executed evidence:** A real fixture with an injected start refusal followed by discard produced:

```json
{"reason":"discarded","ready":["probe-a1"],"held":false}
```

The existing discard test starts from an already held review task, so it cannot detect a missing hold operation.

**Suggested fix:** Ensure every non-done task is queued and held after discard, retaining an appropriate body and reason. Keep done tasks done. Cover queued/unheld, partially held and in-flight inputs, including repeated calls after partial task-store failure. This is separate from the launch-fencing requirement in finding 1.

### 12. A successful side effect followed by an audit-write failure is not repaired on retry

**Severity:** medium  
**Location:** `src/dispatch/finish.ts:57, 114–116, 123–144, 166–178`.

**Scenario:** Treehouse returns a lease, then appending `lease_returned` fails. The response incorrectly says the lease is preserved and instructs another finish. The next call sees `finished` and refuses, leaving the return and operator process confirmation permanently unrecorded. Likewise, an integration followed by an `integrated` append failure is skipped on retry once Git already contains the work, without repairing the missing event.

**Executed evidence:** Injected only the post-return log failure:

```json
{"first":"stopped","reportedLease":"preserved","retry":"refused","returnedRecorded":false}
```

The successful return used real Treehouse. The integration analogue follows from the `integration` construction and append ordering. PRD line 83 promises repeatability after any step failure and recording of each step; current tests fail the return **before** its side effect, not its subsequent log write.

**Suggested fix:** Persist the operator confirmation/intent before destructive return, distinguish side-effect success from recording failure, and reconcile missing completion records on retry. Report current/unknown lease state rather than an unconditional preserved value. Apply this consistently to integration, task recording and discard.

### 13. Finalisation promise rejection bypasses dispatch's structured failure handler

**Severity:** medium  
**Location:** `src/dispatch/dispatch.ts:297, 313–319, 333–348`; `src/cli.ts:202–211`. Related Phase 2 exposure: `src/dispatch/finish.ts:34, 85, 94–99`.

**Scenario:** After worker completion, retention or a finalisation log write rejects–for example, a disk-full append. The outer dispatch try/catch returns `finalise(...)` without awaiting it, so its later rejection escapes the catch. CLI `--json` gets no structured attempt result; the outer CLI handler prints a stack trace and exits 2. Finish also has owner/retention/Git awaits outside its later structured stopped handlers.

**Executed evidence:** A post-worker retention exception escaped `dispatchOnce`:

```json
{"error":"Error: injected retention read failure","lastEntry":"worker_finished"}
```

No compensating halt was recorded. A rejected awaited append inside the same `finalise` promise has the same control flow. The Phase 1 review's post-side-effect structured-error finding is therefore not completely fixed, despite the README's blanket statement.

**Suggested fix:** `return await finalise(...)` inside the enclosing handler, and provide equivalent side-effect-aware boundaries for finish's observations/checks. Preserve known identities, distinguish unknown owner outcomes, and test finalisation append failures, not only the existing `task_started` write failure.

### 14. Resolve mutates records even when the task owner is unreadable

**Severity:** medium  
**Location:** `src/dispatch/resolve.ts:21–45`; `src/dispatch/state.ts:49–51`.

**Scenario:** Ready/in-flight listing works, but reading the selected task fails. Resolve converts the error into diagnostic `task: unreadable`, then records an operator stop and resolution anyway. It does not use the supposedly common unknown-state refusal. Classification also puts possibly-running ahead of unreadable task state.

**Executed evidence:** A logged, reserved, unexited fixture runtime with a failing task read returned:

```json
{"reason":"resolved","observed":{"runtime":"unknown","leaseHeld":false,"task":"unreadable"}}
```

This did not return a workspace, and no process was launched. The substantiated defect is the mismatch with PRD lines 54/102: an unreadable owner must block every command changing that attempt. The common classification is not actually the source of resolve's checks.

**Suggested fix:** Preserve uncertainty independently from the most urgent displayed state, and enforce it in all mutating operations. If orphan-runtime stop confirmation is deliberately an exception, specify that narrow exception and distinguish it from a failed owner read; do not silently treat missing and unreadable alike.

### 15. The tests do not enforce conditional return at the Treehouse boundary

**Severity:** medium  
**Location:** `tests/dispatch/finish.test.ts:278–286`; `tests/workspaces/treehouse.test.ts`; `src/workspaces/treehouse.ts:79`; `docs/phases/02-reconciliation-and-recovery/verification.md:5,12`.

**Scenario:** A regression drops the allocation-ID precondition from the actual Treehouse command. The finish test records the `LeaseIdentity` object passed to the provider, not the arguments the provider sends. The happy-path real return succeeds whether or not it was conditional.

**Executed mutation evidence:** Removed only `"--if-lease-id", leaseId` from the Treehouse return argument list, leaving holder validation and the holder flag intact. **`npm run check` passed, and all 37 finish/Treehouse tests passed.** A separate mutation removing both conditional arguments also left those 37 tests passing. Restored both mutations.

Thus verification's claim that disabling the exact lease identity/holder check makes a test fail is not supported at this decisive boundary. The production code currently supplies both flags; this finding is about regression protection and overstated evidence, not a claim they are currently absent.

**Suggested fix:** Add adapter-level tests asserting the emitted conditional arguments and real fixture tests attempting return with a wrong allocation ID and wrong holder. Verify refusal leaves the current allocation untouched, including a path reused for a new lease. Correct the verification record to name the precise mutations and results.

### 17. Newline-containing worktree paths break integration

**Severity:** low  
**Location:** `src/workspaces/integration.ts:29–30`.

**Scenario:** A valid macOS/Linux worktree path contains a newline. Splitting plain porcelain output on newlines truncates that path; the following merge runs with a nonexistent cwd.

## What was checked and found sound

Within the tested boundaries, the following protections were present and meaningful:

- Normal finish/discard require operator confirmations; discard is the explicit path allowing dirty-worktree destruction. Production Treehouse return currently includes both allocation-ID and holder conditions.
- Accepted output must strictly advance the starting commit, pass retention, and be recorded as the operator's decision before integration/task changes. A remembered acceptance pins the accepted commit rather than automatically accepting later branch commits. Its immediate retention recheck exists and its test detects removal.
- Operator global/context forbids survive repository-layer overrides. Repository JSON uses a strict fixed-kind schema and cannot define arbitrary policy scripts. Ordinary output-branch and working-tree edits do not affect base-policy lookup absent the ref ambiguity in finding 3.
- Happy-path fast-forward integration and non-fast-forward refusal work; unchecked worktree discovery is the separate failure boundary in finding 6.
- Result validation is strict and identity-bound; required evidence/deliverable names and all reported Git/artefact references are checked. Artefacts are constrained to retained storage, with broken/inaccessible links rejected. Dirty/untracked files and unreferenced commits block ordinary code retention; scratch-workspace exceptions are explicit.
- Runtime reservation prevents ordinary same-lease relaunch. No observed child exit is treated as unknown rather than proof of absence. Direct-child exit is not represented as whole-worker termination.
- Attempt publication and sequence-only append filenames protect against partial JSON publication and different-kind sequence collisions. Existing concurrency tests exercise staggered dispatch exclusion and request reservation, in addition to simultaneous creation.
- Sequential pruning preserves unfinished, leased, unknown and possibly-running attempts; its unlogged-lease holder protection is tested. Tombstones support interrupted removal and maintain attempt numbering in the tested sequential schedules. The concurrent reservation-release flaw is distinct.
- Task-store commands explicitly address the configured store, rather than relying on workspace cwd. Large hold bodies use a file, and done notes are bounded. Truncated task CLI output is refused in source, although its adapter-level test gap is accurately acknowledged by the verification document.
- Worker startup isolation flags, result identity, one-prompt behaviour, operator message withdrawal/claiming, and direct-child lifecycle handling have substantive tests. No agent supervisor interpreting arbitrary worker text was implemented in this snapshot.

## Simplifications that would reduce risk

- Use the same unconditional final retention gate for both finish variants; vary only the evidence source. This removes the branch responsible for finding 2.
- Keep “owner observation unknown” separate from the displayed highest-priority state, and reuse one eligibility decision in mutation commands. Current string/suffix-driven classification plus separate command checks causes findings 1, 8, 9 and 14.
- Centralise side-effect/readback/audit outcomes without assuming `lease: preserved` for every caught error. Make retries reconcile facts rather than merely skip work when a target appears done.
- Give pruning a single cross-process ownership model for cleanup and reservation retirement rather than adding more check-then-delete predicates to the existing race.

## Unconfirmed concerns and review limits

These are follow-up concerns, **not additional reproduced findings**:

- GitHub protection uses `/branches/<branch>/protection`, and unknown facts are deliberately permitted with a diagnostic. I did not call a live forge or verify whether all applicable ruleset-based protections are represented by that endpoint. The verification record correctly acknowledges the real `gh api` integration gap.
- The checked-out branch path uses `git merge --ff-only` without the un-checked-out path's expected-old-ref precondition. Concurrent checkout/branch changes between inventory and merge were not reproduced. Likewise, there is no demonstrated cross-process lock covering status/finish/discard owner snapshots through all mutations.
- Dispatch's pre-acquisition resolution read and acquisition are separate operations (`dispatch.ts:219–230`). The existing exclusion test pauses before that read, not after it; a resolution during an in-progress acquisition remains worth a deterministic follow-up. Finding 1 independently demonstrates the pre-launch discard race.
- Prune uses snapshots from separate status/inspect calls and does not revalidate the exact log generation immediately before renaming/removing it. Beyond the reproduced reservation race, concurrent log appends, owner changes, stale creators and prune schedules were not exhaustively explored.
- Git replacement refs, corrupt parent-directory links, hostile same-OS-user rewriting, and power-loss persistence were not qualified. The documented absence of a same-user security sandbox is not itself reported as a new defect.
- Linux/Windows native execution, Windows filesystem sharing/locking and process behaviour, real model/provider failures, live GitHub calls, and the documented real end-to-end Phase 2 run were not independently rerun. CI configuration was read; remote CI claims were not independently verified. Dependency implementations were not exhaustively audited.
- The review read all requested source/tests/documents, but is not a proof of absence of other races or failures. Synthetic peers and fault wrappers do not establish real-agent or cross-platform qualification.
