# Task-store contract

Status: implemented, following the contract agreed on 21 October 2026 with [ADR-0007](adr/0007-one-sqlite-database.md).

Switchboard owns its tasks from ADR-0007 onwards. tasks-axi applied some of these rules implicitly, and some cases it never had to decide, so this contract states every rule the task store must implement and its tests must cover. Readiness is unchanged from tasks-axi.

## Identity

- A task ID is chosen by whoever adds the task, and must be slug-shaped, as tasks-axi requires: letters, digits, `.`, `_` and `-`, with no spaces. It is unique within the database. Tasks are never deleted, so an ID is never reused.
- Task IDs are not scoped to a context: one database's tasks are shared by every context that uses it, and each context selects tasks by repository, as it did with a shared tasks-axi backlog.
- A request ID is unique within a context. The same request ID may be used in two contexts. Request records are separate from attempts and never expire, including after pruning.

## States and holds

- A task is `queued`, `in_flight` or `done`. A hold is separate from the state: a held task keeps its state and has a hold reason.
- A hold reason is one line of at most 200 characters, as now.
- Only dispatch marks a task `in_flight`, after acquiring its lease and in the same transaction that records `task_started`. The operator's commands never do.

## Dependencies

- A task can be blocked by other tasks. A dependency on the task itself, on a task that does not exist, or one that would create a cycle, is refused, and nothing changes.
- The import drops a dependency on a task that does not exist and reports it. tasks-axi treats such a blocker as done, so readiness is the same with or without it.

## Readiness and order

- A task is ready when it is `queued`, not held, and every task it is blocked by is `done`.
- Every task has a position, unique within the database. A new task goes after every existing task. Ready tasks are listed, and taken by dispatch, in order of position, filtered by repository.
- Readiness is checked when an attempt is created and again when its task is started. It is never re-checked for an attempt that has started: holding the task, adding a dependency or changing its instructions takes effect at the next dispatch, not on a running attempt.
- Reopening a task that others are blocked by makes them blocked again from then on. A dependant that has already started or finished is unaffected.

## Definition revisions and attempt specifications

- A task starts at `definitionRevision: 1`. Changing its title, body (instructions), repository, kind or ordered acceptance criteria increases the revision in the same transaction. One update changing several fields increases it once; a no-op update does not. Holds, releases, dependencies and state changes alone do not change it.
- Reservation stores an immutable specification in the same transaction as the attempt: task and context IDs, definition revision, title, resolved instructions (the title when the body is blank), ordered acceptance criteria, repository, kind, backing repository, base ref, output branch, resolved delivery contract and non-secret runtime settings. The runtime snapshot includes the Pi profile, executable and entrypoint, provider, model, thinking level when configured, shell tool, timing settings and usage limits. Configuration selectors record which file supplied a value, or that it used a default. Neither credentials nor the worker's environment are copied.
- Acquisition records a separate immutable allocation: lease, workspace, backing repository, pool, output branch and actual starting commit. The worker's input is built from the stored specification and allocation, not from a later task or configuration read. `status --json` reports both, with `specificationComplete`.
- Starting checks both readiness and the definition revision in its transaction. A definition changed during acquisition halts the attempt as `task_definition_changed`, without a launch, and keeps the unused lease. It holds the task unless a newer operator hold or state decision already applies. Return the unused lease through Treehouse, record its return with `resolve --lease <lease-id> --lease-returned`, check and release the task, then dispatch a new attempt. Switchboard never returns that lease automatically.
- Existing attempts are migrated from their stored runtime bindings. Facts and configuration provenance not retained by those bindings are left missing or marked `unknown`, never guessed from today's task or configuration. An attempt without a complete specification remains inspectable, fenceable and resolvable, but cannot start or obtain permission to launch.

## Starting from an earlier attempt

The reservation-only operation `reserveFromAttempt` in `src/dispatch/reserve.ts` accepts an explicit task, a stable request ID and `startingPoint: { taskId, attempt }`. It reads owner evidence and checks Git retention before calling the shared `AttemptStore.reserveAttempt`. It acquires no workspace, changes no task state and launches nothing. `dispatch --once --task <id> --from-attempt <n> [--note <text> | --note-file <path>]` uses that reservation, then acquires a new workspace and launches once. This is a separate request, never a retry of the earlier worker. An omitted request ID is generated for this request. A dry run checks the reservation's safety, readiness, capacity and attempt limit without writing it.

The source must belong to the same task, be settled with known owner state, and have an observed child exit or a scoped `worker_stopped` confirmation. A finish entry alone is not exit evidence. Unknown state, missing records, an unrecorded or unretained output commit, or any possibly running worker refuses without reserving the request ID or changing records. Other attempts and unrecorded leases still block as for ordinary dispatch. Only the named source's retained lease is exempt; ordinary dispatch remains blocked by it. Held tasks must be released and done tasks reopened explicitly.

The new immutable specification has optional `startingPoint: { taskId, attempt, commit }` and a written `handover`. The handover is prepared before reservation and stored in its transaction: task instructions and criteria, earlier outcome and summary, the exact commits since its starting commit, criteria report, recorded findings and evidence, and the requester's note. Later task edits, operator notes, branch movement or result-file changes cannot rewrite it. Worker instructions append this stored handover; status and watch show it. The commit comes from the source's recorded validated result's output-branch reference, or its exact accepted output commit when output was accepted. Neither a later branch head nor a changed result file replaces it. Retention checks only that exact commit on the recorded output branch; the old workspace can already have been returned, and uncommitted files are not inherited. Reservation rechecks the observed attempt entries and confirmations, launch permissions and exits in its transaction. A source cannot obtain fresh launch permission after a continuation is reserved, including after that continuation is archived. The new attempt has its own request ID, number and output branch; its later lease and session are not copied. Worker input refuses an allocation whose starting commit differs from the recorded starting point. Treehouse accepts branch names, not raw commits, as bases, so the adapter creates a private `switchboard-starting-points/<SHA-256 of output branch>` ref at the recorded commit using create-only `git update-ref`. Treehouse creates the new output branch from that ref and the adapter verifies the acquired HEAD. After recording the allocation, dispatch removes the private ref; it also removes it if the attempt closes without an allocation. Prune uses the same cleanup operation for refs left by an interrupted acquisition, regardless of retention age, once the attempt has an allocation or is closed. Cleanup uses conditional `git update-ref` deletion with the recorded starting commit as the expected value. A moved ref is left and reported, never moved back or deleted. A cleanup failure is reported without blocking dispatch or changing the attempt's outcome. Prune keeps records whose ref could not be removed for inspection and a later cleanup. Preparation is never repeated for the reservation. The allocation and worker delivery both record the actual starting commit. Retention requires code attempts to add commits beyond their own starting commit, not merely inherit earlier output.

`maxAttemptsPerTask` (default 3) counts all lifetime reservations for the task across contexts sharing the database, including archived attempts. It is checked in the reservation transaction alongside capacity and readiness. Concurrent reservations cannot pass the limit. A request replay returns the original attempt before these checks; a crash during the transaction leaves no partial number, request, attempt or specification.

## Review tasks and findings

`review --task <id> [--attempt <n>]` creates a new queued task of kind `review`, not another attempt of the source task. Its immutable `review_tasks` row names the context, reviewed task and attempt, exact output commit, output branch and source session when known, with the original attempt's criteria and backing repository. A foreign key refers to the source's retained attempt number. Task creation and the target row are one transaction, after checking stopped-worker and retained-output evidence. The review instructions ask for each criterion to be judged against the exact commit. Later edits to the source task cannot change these inputs.

Dispatch reads and checks the target before reservation, including on a dry run. The reservation transaction checks the source snapshot and its recorded commit again, and requires the review task still to have kind `review`, the original criteria and the same backing repository. It copies `reviewTarget` into the immutable specification. A review cannot also use `--from-attempt`. Acquiring its workspace uses the same pinned starting-commit mechanism and ref cleanup as an earlier-output reservation. Both worker-input construction and launch permission refuse the source session ID or a different starting commit. Creating a review prevents the source from gaining fresh launch permission.

The review result uses the existing `criteriaReport` and must include a Git reference named `reviewed-output` with the exact source branch and commit. Recording the review's task outcome also appends `review_recorded` to the source in the same transaction, using the immutable validated result, an observed worker exit and the stored specification. The record names the review task and attempt, exact commit, `passed` or `failed`, and each criterion's findings. Only a retained completed result with every criterion met passes. An invalid or missing result records no judgement. Recording refuses if the source's recorded output commit has changed. Replaying a request cannot duplicate findings. Review does not change the source task's state or acceptance.

Status reports findings for the current recorded output commit; old findings remain in the attempt entries and are copied into its archive summary when pruned. A missing or archived source cannot be reviewed, so retain its live records until review completes. A later continuation's handover includes recorded review findings with the source entries. A review is another worker's judgement, not proof.

## Request records and pruning

- Reservation writes the request record and attempt in one transaction. The record names the selected task and attempt, even when the caller requested automatic selection. A replay returns that attempt, never selects the next ready task and never acquires a lease or launches or prompts a worker.
- Starting-point requests also include `"startingPoint":{"taskId":"<source task>","attempt":<source number>}` after `taskId` in the canonical fingerprint object. Both fields are caller inputs; a supplied handover note is also included as `note` (the text read from `--note-file`, not its path). The resolved output commit is stored in the specification, not in the fingerprint. Omitting the starting point preserves existing version 1 fingerprints. Reusing an ID with another starting point, or without its original starting point, refuses as `request_input_mismatch`.
- Encoding version 1 fingerprints the canonical UTF-8 JSON object `{"taskId":null}` for automatic selection, or `{"taskId":"<explicit ID>"}` for explicit selection, using SHA-256. The context scopes the key; the request ID is not an input to its own fingerprint. Configuration, resolved contracts, current task definitions, cancellation signals and dry-run mode are not explicit task-selection inputs. A dry run does not reserve an ID. Reusing an ID with different explicit inputs refuses as `request_input_mismatch`, before and after pruning. An unreadable request record is an error, never absence.
- Pruning writes the archived summary, switches the request record to that summary, removes the attempt and its entries, and schedules runtime directory deletion in one transaction. Deletion follows outside the transaction and can be resumed. Request records and attempt numbers stay indefinitely; pruning does not change tasks, leases or output branches. Private starting-point refs are cleaned up separately as described above.
- Schema version 6 migrates existing reservations and request IDs in archived summaries, including legacy file imports. Historical records use encoding version 0 with an unknown fingerprint because the old records did not distinguish explicit from automatic selection. They still exclude reuse: a provably different task refuses as `request_input_mismatch`; otherwise dispatch refuses as `request_reserved` and asks for inspection, without launching. An orphan reservation can be linked to an archived attempt only when its task agrees. Conflicting historical tasks or attempt numbers for the same context and request ID refuse the migration transaction rather than choosing one.

## Changes during an attempt

- The operator can change any task at any time, including while an attempt runs, for example to hold it, record it as done, or change its body. A definition change after start neither changes nor cancels the running attempt's input; it applies to a later attempt.
- Recording an attempt's outcome changes the task only if it is still `in_flight` and has not been held since the attempt started it, in the same transaction as the outcome's log entry. If the operator has changed the task's state or held it in the meantime, the outcome is still recorded in the attempt log, the task is left as the operator set it, and `status` reports the disagreement. Finalisation never overwrites a newer operator decision.
- `finish` and `discard` record a task as done or held only after checking, in the same transaction, that it is in the state the command expected.

## Acceptance criteria

Schema version 8 adds each task's ordered `acceptanceCriteria` list, initially empty. Add and update accept nonempty single-line criteria, including repeated text at different positions. Changing their order or content increases the definition revision once with any other definition changes; replacing them with the same list is a no-op. The stored attempt specification and worker input retain that attempt's list even when the task later changes.

`task add` and `task update` accept repeatable `--criterion <text>` or `--criteria-file <path>` (one criterion per line, ignoring blank lines). An empty file sets an empty list. Show and JSON output include it.

`task convert-criteria` moves a flat bullet list from a single `## Acceptance criteria` body section into the list and removes the section, in one transaction. It reports each converted task and each section left unchanged with a reason. It processes the configured repository's queued tasks, including held ones, never in-flight or done tasks. Nested or multiline lists, prose, empty or repeated sections and existing stored criteria are left unchanged. Headings in fenced code are not sections. Re-running does not change already converted tasks.

## Commands

The `switchboard task` commands (add, show, list, ready, update, hold, release, block, unblock, done, reopen, convert-criteria) apply these rules. Each change is one transaction, each command takes `--json`, and a refusal changes nothing and gives a stable reason code.
