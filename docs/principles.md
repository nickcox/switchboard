# Switchboard principles

1. **Give each fact one authoritative owner.** Switchboard owns work, readiness and attempts, Treehouse owns leases, and the runtime adapter owns liveness. Do not maintain competing copies.
2. **Reconcile observations before acting.** A disagreement is a condition to inspect, not permission to overwrite an owner's state. Unknown is distinct from absent.
3. **Add persistence only for a required fact.** First identify what must survive a restart and why an existing owner cannot hold it. Tasks and attempts are such facts: no other owner records which task, lease, session, commits and outcome belong together. Switchboard keeps them, and its records of the workers it supervises, in one database ([ADR-0007](adr/0007-one-sqlite-database.md)); only what a worker writes itself stays in files.
4. **Carry identity across boundaries.** Preserve task ID, lease ID and runtime session identity. Check all three before accepting a worker result or releasing its workspace.
5. **Treat partial failure as normal.** A change within Switchboard's database is one transaction, but operations across Switchboard, Treehouse and the runtime are not atomic. Define compensation for those, distinguish confirmed failure from an unknown outcome, and avoid blind retries.
6. **Match caution to whether an action can be undone.** Returning a workspace can destroy work, so it requires evidence that the work is retained and nothing is still using the workspace. Task transitions, holds and reports can be corrected later: after an uncertain outcome, read the owner's state back and continue if it is confirmed, or record the disagreement for the operator. Do not design a refusal path for every reversible step.
7. **Preserve work when uncertain.** Do not return a workspace while a worker may still be using it or while work may be lost. Keeping a workspace costs disk space; losing one can cost work. Surface the reason and the next operator action.
8. **Keep providers replaceable.** Dispatch policy depends on task-store, workspace-provider and worker-runtime interfaces. Switchboard's database, Treehouse and Pi are the current providers; their models may inform the interfaces, but their integration details stay inside adapters. Runtime adapters own execution mechanics; Switchboard owns dispatch policy. Workers report outcomes and do not independently change orchestration status or release leases.
9. **Keep domain rules independent of Pi Durable.** Switchboard defines mailbox and schedule semantics. Pi Durable supplies later persistence and execution primitives; its computational tasks do not replace Switchboard's tasks, which are project work items.
10. **Design operations for an agent supervisor.** Supervision is expected to be done by an agent. Switchboard owns the mechanics and safety rules; the supervisor owns judgement about what to do next. An operator can perform every operation under the same policy, without a supervisor. Switchboard itself enforces which operations need operator approval; instructions to an agent are not enforcement.
11. **Start with one host and one dispatcher.** Never dispatch the same task twice. Phase 1 supports one dispatch at a time without enforcing it; Phase 3 enforces a maximum number of attempts in the database. An unresolved attempt blocks its own task until the operator resolves it; it blocks other dispatch only while its worker may still be running. Add broader concurrency and distribution only with explicit ownership and recovery rules.

See the [architecture](architecture.md) for ownership and the [Phase 1 PRD](phases/01-basic-dispatch/PRD.md) for concrete behaviour.
